# 多 Agent 协作 — 学习复习笔记

> 主题：多 agent 系统的拓扑、实现机制、真实效果、边界与局限；agent/workflow 的区分；
> 以及本项目（结构化拒绝、治理动词）在多 agent 语境下的位置。
> 数据口径来源：Anthropic《Building Effective Agents》(2024.12)、《How we built our multi-agent research system》(2025.6)，及本仓库实践。

## 0. 一句话本质

多 agent 不是神秘架构，就三个组件：**编排层**（谁分派任务）+ **上下文隔离**（每个 agent 独立的干净窗口）+ **通信契约**（结果怎么回传）。设计含量集中在后两者。

## 1. 主流拓扑（按可控性排序）

| 拓扑 | 形态 | 适用 | 现状评价 |
|---|---|---|---|
| **编排者-工作者**（orchestrator-workers） | 主 agent 拆任务 → 子 agent 独立跑 → 返回**结构化摘要** | 可并行分解的研究/搜索/审查 | **业界最稳、事实标准**（Anthropic 研究系统、Claude Code 子 agent 机制均是） |
| 流水线（pipeline） | A 的输出是 B 的输入，串行 | 阶段清晰的转换（抽取→验证→汇总） | 稳；本质是 workflow |
| 并行 fan-out + 汇总 | 同构任务撒出去，map-reduce | 批量核验、多源调研 | 稳（本项目调研阶段 75 票对抗验证即此） |
| 对抗式（adversarial） | 生成者 vs 验证者/红队 | 事实核验、代码审查 | 好用；验证者必须拿**独立证据**而非复述 |
| 自由群聊（早期 AutoGen 风格） | 多 agent 共享消息总线互聊 | — | **实践中失控，业界基本退潮** |
| 显式图/状态机（LangGraph 类） | 节点=agent/工具，边=转移条件 | 步骤可枚举的业务流 | 严格说是 workflow——把确定性从 LLM 手里拿走 |

## 2. 实现机制（工程细节）

- **上下文隔离是核心价值，不是副产品**：单 agent 长任务会 context rot（上下文越满召回越差）；子 agent 各拿干净窗口，只回传千字级摘要，主 agent 上下文只装结论不装过程。
- **任务描述必须自包含**：子 agent 看不到主对话——最大新手坑。派活时背景、假设、产出格式、边界全部写进简报，一个"它"都不能有。
- **返回走契约**：结构化输出（分节、来源标注、置信分级），主 agent 按契约消费而非自由文本。
- **共享状态走外部存储**（文件/数据库），不走消息传递——大对象在消息里传会撑爆双方上下文。
- **并行调度**：无依赖任务一次并行发出；有依赖串行；每个子 agent 设轮次/预算上限防跑飞。

### 2.1 子 agent 输入/输出：动态还是手工？

实践共识 = **混合：结构手工定死，内容动态生成**。

- 输入侧：任务简报的**骨架**是人手工设计、按失败案例迭代的固定模板（目标/背景/方法/产出格式/边界五要素）；主 agent 每次动态填内容。纯动态派活质量方差大——Anthropic 研究系统早期就因 lead agent 派活模糊导致子 agent 重复劳动，修法是给主 agent 写死"派活必须含哪五样"。
- 输出侧：契约手工定死且可解析（消费端要按契约编程）。
- 真实问题：①契约遵守非 100%（数字漏标来源分级，主 agent 得兜底核对）；②**隐含上下文丢失**（主对话积累的偏好、否决过的方向没进简报 → 子 agent 重走死路）；③过度/欠指定的平衡只能靠迭代。

## 3. 多 agent vs 单 agent 串行：真实效果

**取决于任务形状；多 agent 赢时，赢的主要不是时间，是上下文质量**（反直觉重点）：

- **广度可并行**（多源调研/批量核验/多维审查）：多 agent 明确赢。Anthropic 内部评测研究类任务提升约 90%——原因是单 agent 串行做完 10 路搜索时上下文已被前 9 路原始输出污染（注意力稀释）；子 agent 干净窗口深挖一路、只回摘要。代价：token 约 **15 倍**。
- **深度串行依赖**（写代码等）：**单 agent 赢**。传递损耗+合并冲突+风格漂移吃掉全部收益。业界印证：编码工具主流形态都是"单主 agent 亲自写码 + 短命子 agent 只做搜索/审查/验证"。
- **逐字精确任务**（一手数字、关键引文）：只能主 agent 亲做——子 agent 取不到时会编造"看起来对的"（本机实测已写入全局规范）。

### 3.1 协同特有的不可解决问题

1. **错误复合放大**：可靠性做乘法——每环 90%，五环串联 ≈ 59%。只能缩短链条+加验证，不能取消数学。
2. **无共享心智**：agent 间只有消息和文件，隐性判断依据（"我为什么这么觉得"）传不过去。
3. **一致性仲裁无根本解**：两个子 agent 结论相左，投票/对质只是缓解。
4. **验证者也是模型**：编造只能被**模型之外的真值锚**（原始 URL、可重跑命令、人工抽查）戳穿，不能在生成层根除。
5. **无可问责主体**：审计能记录，责任仍要落到人——高风险写入永远需要治理管线+人审。
6. **经济性天花板**：15 倍 token 换不到 15% 增益的场景很多。多 agent 是**广度任务的重武器，不是通用架构**。

## 4. agent vs workflow（标准定义）

出处：Anthropic《Building Effective Agents》。

- **Workflow**：LLM 与工具按**预定义代码路径**编排——每步做什么写在代码里，LLM 只在节点内做局部判断。可预测、可测试、可回归、成本可控。
- **Agent**：LLM **自主决定过程与工具使用**——下一步调什么、何时结束由模型定。灵活扛开放任务，代价是不可预测。
- **判据一句话：谁拥有控制流。** 循环写在代码里 = workflow；模型决定循环何时停 = agent。
- 两者是谱系不是二元：单次调用 → 提示链 → 路由 → 并行化 → 编排者-工作者 → 评估-优化循环（以上均为 workflow 模式）→ 自主 agent。
- 选型：步骤可枚举/要确定性/要控成本 → workflow；路径事先不可知（调研、调试、模糊需求）→ agent；**最常见是混合**——外层 workflow 钉死阶段，阶段内 agent 自主。
- 本仓库实例：`examples/daily-patrol.sh` 是 workflow（物化→巡逻，顺序定死）；巡逻那步内部是 agent（模型自主决定扫描→逐个落账→写研判的调用序列）。

## 5. 最佳实践清单

1. **默认不用多 agent**：能单次调用别 workflow，能 workflow 别 agent，能单 agent 别多 agent。
2. 启用的三个正当理由：可并行分解且并行收益明显 / 单上下文装不下 / 需要角色对抗（独立验证）。
3. 拓扑选编排者-工作者；避免自由群聊。
4. 子任务自包含简报（五要素模板）+ 返回契约化（结构+置信分级）。
5. 共享状态外置（文件/DB）。
6. 确定性流程下沉状态机，LLM 只留判断节点；状态机节点的动作仍调治理动词。
7. 建端到端评测集（评终态不评过程），否则改动无法回归。
8. 高风险动作设人审节点。

## 6. 本项目的关联实现：结构化拒绝（多 agent 安全写入的收敛点）

论点：**多少个 agent 并发，写入口只有一条治理管线**——护栏长在写入口上，不靠 prompt 求自律。支撑机制是"结构化拒绝"：

- 类型层（`packages/engine/src/actions.ts`）：拒绝是三态可辨识联合，不是异常——
  `{ok:true,…} | {ok:false, stage:'params', message} | {ok:false, stage:'criteria', failedCriterion, message}`。
- 执行器：参数校验给到具体字段与期望类型；criteria 逐条命名求值，失败返回该条 apiName + 人话 message（如 `cashSufficient：现金余额不足以完成买入`）。
- HTTP 层：**业务拒绝也是 200**——拒绝是合法业务结果，结构化透传，HTTP 层不翻译业务语义。
- AI 层闭环：工具描述**事前预告**前提清单；`call()` 把拒绝结构原样塞进 tool_result **事后告知**违反了哪条——模型形成"知道规则→知道违反原因→针对性调整"（查现金→调小数量→重试）的自纠回路，而非瞎重试。
- UI 层吃同一份结构（前提清单红叉标失败项）——**人和 AI 读的是同一种拒绝**。
- 对照反面：只返回 `500 "failed"` 时模型唯一能做的是原样重试或放弃。结构化拒绝把治理规则变成了**模型可学习的环境反馈**。

## 7. 一分钟对外讲解版

"多 agent 我实际用过两种形态：并行调研（三个自包含子任务、来源分级契约返回、主线亲自复核关键数字）和对抗验证（一百余个验证代理逐条拿原文对质）。我的结论：编排者-工作者拓扑加契约化返回是目前唯一稳的形态；多 agent 赢在上下文隔离带来的质量、而不只是并行省时间；它最大的敌人是错误复合放大和子 agent 编造。所以在本体项目里我把所有写入收窄到带前提校验和审计的动词上——多少个 agent 并发，写入口只有一条治理管线，且拒绝是结构化的，模型读得懂、能自纠。这比在 prompt 里写规矩可靠得多。"
